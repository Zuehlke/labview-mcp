1 · What is an MCP

The model knows LabVIEW. It cannot touch it.

An LLM will happily discuss a queued message handler. It cannot open your project.

What it cannot do on its own

  • Open your .seq or your .lvproj
  • See whether a VI is broken
  • Run a sequence and read the result
  • Write a file back where you wanted it
Without an integration, copy-and-paste is the interface — and a screenshot of a block diagram is not something you can execute.

MCP — Model Context Protocol

An open protocol for connecting an AI host to a tool. The model does not call your API; it calls a tool you declared, and your server makes the API call.

  • Open — a specification, not one vendor's feature
  • One server, any host — Claude, Codex, Copilot, a local LLM
  • You keep control — the server runs on your machine, under your account

1 · What is an MCP

The shape of it

Four boxes. The middle two are the protocol; the outer two are yours.
Both servers here are .NET 8 console applications speaking stdio. There is no cloud hop: the model asks its host to call a tool, and the host runs the executable sitting next to LabVIEW.

1 · What is an MCP

What a server exposes

Three kinds of thing — and in practice, one of them does the work.

Tools

Callable functions with a JSON Schema for their arguments. run_sequence, lvai_generate_vi. The model picks one and fills in the blanks.

Resources

Documents the host can read on demand. The LabVIEW server publishes its five reference manuals as labview://aixml-reference and friends.

Prompts

Canned workflows a user can invoke by name. Useful; neither server leans on them.

The schema is the documentation

There is no manual for the model to read. It sees the tool name, the description you wrote and the parameter schema — that is the entire contract. A vague description is a bug, and it produces wrong calls rather than an error message.

Annotations let the host gate the writes

readOnlyHint destructiveHint — of the LabVIEW server's 80 tools, 33 are read-only and 25 are marked destructive, so reads run without a prompt while anything that writes a .vi still has to ask.

2 · TestStand MCP

Standing on NI's own API

The Sequence Editor is a client of it. So is this.
  • The TestStand API is public, documented and versioned. Engine, SequenceFile, Sequence, Step, Execution, Thread, PropertyObject — the same object model NI's own editor is built on.
  • Nothing was reverse engineered. Every call in this server is in the reference manual.
  • So the work moved up a level: not can I reach it, but what shape should the tool have so a model uses it correctly.
That is the whole difference. On TestStand I spent the time on surface design, verification and guard rails. On LabVIEW I spent it on discovery.

Practical consequences

  • x86 build — the engine COM server is 32-bit, so the whole process is
  • Lazy connect — connect_engine, then everything shares one engine
  • .tsenv environments — the same isolation the editor's /env switch gives, in-process and verified after connecting
  • Undo groups — a multi-step edit is one transaction the operator can revert

2 · TestStand MCP

The parts that are more than a wrapper

A thin wrapper over an API is easy. These are where the value is.

Whole-file export / import

The entire sequence file as one JSON model — types with their attach state, file globals, every sequence with parameters and locals, every step with its full module configuration — and rebuilt elsewhere. This is how you migrate, clone or bulk-edit. The granular tools are for surgery.

Native diff

Not a text diff of an XML dump — the same FileDiffer the Sequence Editor uses, with category, path and change-type filters. A "looks clean" result means what TestStand means by it.

Three verification tools

validate_sequence_plan checks a planned step list before anything is built — unclosed blocks, undeclared variables. audit_sequence_references finds undeclared Locals. / Parameters. use. audit_type_consistency catches duplicate or mismatched type registrations, which a content diff cannot see.

Live thread context

Read and write a running or paused thread's runtime state: live variable values, the execution cursor, Set Next Step. The ordinary expression tools cannot reach that scope — this is the Variables pane, over MCP.

Module settings verified by read-back

Every module setting is read back after it is written, so the result reports what actually landed on the step. A target that could not be resolved is named, not silently accepted.

Analyzer that admits when it did nothing

The Sequence Analyzer loads every code module, so a big file runs for minutes — hence an async mode with polling. And zero messages is reported as resultSuspect, not as "clean", because it almost always means the run did not happen.

2 · TestStand MCP

Why I call it feature complete

  • Every phase of the workflow is reachable. Author a file from nothing → analyse it → run it → debug it live → read the report. No step drops back to the GUI because the API would not go there.
  • No capability needed a workaround. There is no chapter in this project called "how I got around the API", because there was nothing to get around.
  • Failures report what TestStand said. The engine's own error surfaces, rather than a generic "tool failed".
  • What is left is polish. Better descriptions, better defaults, more guard rails — not more reach.

3 · LabVIEW MCP

A very different starting point

There is no TestStand API for LabVIEW code generation. There is a gRPC server nobody documented.

The plumbing is NI's, and it is public

The server inside LabVIEW is ni/grpc-labview — NI's own open source, MIT licensed. It is a generic server: it serves whatever schema LabVIEW registers into it at runtime, and it ships with gRPC reflection switched on so a client can ask what that is.

We asked. It answered.

What it happens to be serving is another matter

lvai.LVAI — the interface behind NI's own LabVIEW coding assistant. No .proto in the install, no documentation, no version policy, and no promise any of these 23 RPCs will be there next quarter.

Said plainly, because it belongs on the slide: this project is not affiliated with, endorsed by, or supported by NI. Nothing was cracked open to get here — but nothing here is promised to keep working either. After a LabVIEW upgrade, dump the schema and find out what moved while you were asleep.

3 · LabVIEW MCP

AIXML — the currency

A VI, as an XML document: nodes, terminals, wires, structures, constants.

Read

Export any VI — including all 951 shipping examples — and read how NI wired it. Installation VIs are cached on disk.

Check

Validation is cheap and names the node and terminal. It is also not a subset of conversion — sometimes stricter, sometimes blind.

Write

Conversion writes a real VI. And this is where the restrictions live.

3 · The restrictions

The single biggest one:
a generated VI cannot call your own code.

Error 53 — Unsupported SubVI
There is no target syntax that reaches project-local code. Not a bare name, not a full path, not a library-qualified name.

I measured how much that costs, structurally, over a production codebase — 900 VIs, using the binary parser, no LabVIEW needed:

VIs that call the project's own code634  · 70.4 %
subVI calls going into own code1 654  · 87 %
VIs with no blocking construct at all136  · 15.1 %

Confirmed from a second direction

NI's own example corpus, exported and re-validated, failed 737 times out of 1 052 for exactly this cause — 70 %.

Two codebases, two methods, the same number. This is not one project's style.

Worth knowing what is rare, too: Timed Loop is on NI's not-supported list and appears in one VI out of 900. Effort spent there would have been effort wasted.

And then the rest of them

Each one cost a session to find. Most of them fail silently.

3 · Workaround 1

The placeholder socket

How a generated VI comes to call your code anyway.
  1. A loose VI under user.lib resolves by bare name. That is a target AIXML is allowed to create.
  2. So generate a placeholder whose connector pane exactly clones the VI you actually want to call. Cached by signature.
  3. Author the call to the placeholder. Validation passes, because the target exists.
  4. Then let LabVIEW re-point it — its own Replace swaps the node onto your VI, and re-types the wires while it does.
That last property is what makes class code reachable: the two panes need not match, so a test authored against path stand-ins becomes a test that calls a real accessor.

What this unlocks

  • A generated unit test calls its subject as an ordinary static subVI — not through VI Server
  • A generated method reads its own class fields through its accessors
  • Generated code composes with the rest of the project
The clone must be exact. A Variant stub retargeted onto a double subject is Error 7, Bad Linkage. The pane's type descriptor is part of the link binding — there is no generic placeholder.

3 · Workaround 2

A second engine, with no LabVIEW in it

Reading and rewriting the VI binary directly — via a bundled pylabview.

The division of labour

AIXML creates and names.
pylabview edits and reads.

The dependency runs one way: every primitive name and terminal role pylabview annotates with was harvested by joining against AIXML exports. It cannot author a VI from nothing — there is no empty starting point.

No LabVIEW, no licence, no Python installation — the bundle ships its own interpreter. These five tools work on a checkout, on a build agent, in CI.

What it actually fixes

  • Connector pane pattern — repaired without regenerating, so no caller changes
  • Diagram comments — placed on the node you meant, with clearance scoring
  • Event specifications — written back after conversion collapsed them
  • Malleable VIs — the four inline flags AIXML cannot write
  • Timed Loop timing — through the wired constant, the only writable place
And a router: pylv_route decides which engine a given edit belongs to, with the evidence, rather than by habit.

3 · Workaround 3

Drive NI's own code

Some artefacts are compiler output. You cannot write them — you have to ask LabVIEW to.
A class private data control looks like a .ctl with a cluster in it. It is really a type space plus a data-space layout. Building one from outside produced, for weeks, classes LabVIEW reported as fine and its compiler refused.
  • The IDE's own project providers are ordinary VIs. They live under resource\Framework\Providers\ and a generated helper can call them.
  • So classes, accessors and Actor Framework messages are created by NI's own wizard code, driven over VI Server — not written by us.
  • And vendor toolkits the same way. DQMH's and LMock's scripting VIs sit under project\, which AIXML cannot reach in any spelling — but Open VI Reference takes a path and has no such restriction.

Ask first: does LabVIEW compile this?

If yes, do not try to write the file. That is the rule that came out of it, and it generalises past classes.

The trick that makes it tractable

Values move as Variants and never have to be named. DQMH's module list is an array of six-field clusters — carried from one Ctrl Val.Get straight into a Ctrl Val.Set, the helper never spells that type out. It applies to any refnum- or cluster-heavy vendor API.

3 · Architecture

Five doors into LabVIEW

Picking the wrong one is the most expensive mistake available. So the router asks first.

The class is created by NI's own provider VIs, the tests call the accessors as ordinary static subVIs, and the report is read back from the suite's own XML.

Where it is genuinely good

  • Boilerplate with a shape — classes, accessors, test suites, message classes, DQMH modules
  • Reading unfamiliar code — export a VI and ask what it does
  • Finding NI's answer first — 951 examples, indexed and searchable
  • Documentation nobody wants to write

Where it is not

  • Editing a VI whose front panel is the point — an edit re-decides the layout
  • Anything where a modal dialog can appear unattended
  • Your 70 % — diagrams that are mostly calls into existing project code

So the optimisation target is the number of calls, not the cost of one. lvai_validate_aixml runs in 0.08 s. Shaving milliseconds off it is worthless; removing one round trip is worth seven seconds.

This is why the server has 80 tools rather than 23 thin wrappers. Nearly every one of them exists because some sequence of calls was measured to be expensive.

How you find the next tool to write

Measure a whole run, then look for the step whose wall clock is large and whose tool time is not.

The biggest single item in one cold build: authoring a test-suite runner — 186 s of wall clock against 6.1 s inside LabVIEW. The model re-deriving XML whose shape never varies. That is now one call.

What generalises

Six things I would tell myself in August

Ask the artefact, not the process

"There is one build and one packaging path" was true of the pipeline and said nothing about what was on the release page. One API call settled in seconds what reasoning had hidden for days.

A plausible fixture is not a test

Both tools that failed on first real use had passing unit tests written against a fixture that looked right. Build the fixture by unwrapping the real artefact.

A fix is not verified by the test written beside it

One filter passed its own test, validated against LabVIEW, and was completely inert. What found it was reproducing the original failure.

Leave the word "cannot" out

An impossibility claim written in the same voice as a measurement stops the next person looking. One such sentence cost 18 days; the fix underneath it was four lines.

Silent success is worse than a loud failure

Almost every expensive bug here was something reporting errorCode 0 while doing nothing — or doing something else.

Write the rule where the work happens

A rule that lives only in an agent's definition is invisible to the route that does not spawn one. Put it in the checker, not only in the document.

Before you point it at code you care about

Two different risk profiles

TestStand MCP

  • Built on a supported, documented API
  • Breaks when NI deprecates something, on NI's own schedule and with notice
  • Still writes and runs tests — the usual care applies

LabVIEW MCP

  • Not affiliated with, endorsed by or supported by NI. Please do not open a ticket with NI about it
  • An undocumented interface: a LabVIEW update, a tweak to the AI feature, a shifted comma in the XML dialect — any one is enough
  • After every upgrade, dump the schema and see what moved
Both of them write and run code on your machine. Work on copies. Commit first. Keep the mutating tools behind a confirmation prompt, and do not allow-list a whole server just because the prompts are irritating. They are irritating on purpose.

Try it

Two commands, or one config line

LabVIEW MCP — as a plugin

claude plugin marketplace add Zuehlke/labview-mcp
claude plugin install labview-mcp@zuehlke-labview

No clone, no build, no config file. You get the server, the eight agents, and a read-only allow-list so reads run without a prompt. Needs Windows and LabVIEW 2026 Q3 running.

TestStand MCP — download and register

"mcpServers": {
  "teststand": {
    "command": "C:\\path\\TestStandMCP.exe"
  }
}

Then: "Connect to the TestStand engine and open my sequence file." Needs TestStand 2019+ and the x86 .NET 8 runtimes.

Any MCP client works — Claude Code and Desktop, Codex, GitHub Copilot, a local LLM. Neither server is tied to one host.
